## How I think about software and AI

I love building systems that work, but I care just as much about *how* those same systems behave once real people start using them.

That means asking questions like:

- What happens when the input is missing, invalid, duplicated or otherwise unexpected?
- What breaks after a change, and how do we account for it in the future?
- What does the system do *when* (not if) things don't go according to plan?
- Can someone else understand, test and maintain the code that was built without the original architect being on perpetual standby?
- Does the implementation actually match the client's stated requirement?


That mindset shows up in the way I build, debug, test, document and improve software.

## Featured Project

### [Mechanic Shop REST API](https://github.com/jenkauppila/mechanic_shop_api)

A production-deployed backend API for managing customers, vehicles, mechanics, service tickets and inventory.

This originally began as my Coding Temple backend capstone, but I later returned to it independently to take it beyond the original course requirements. I reviewed the public API as if I were preparing someone else's software for real users, including: testing behavior, finding security and data-quality issues, documenting reproducible defects while correcting any documentation drift, and hardening the live demo.

**What the project demonstrates:**

- Python, Flask, SQLAlchemy, PostgreSQL/Supabase
- Relational CRUD APIs and many-to-many relationships
- JWT authentication and ownership checks
- Automated pytest coverage for expected behavior, invalid inputs, authentication failures, API errors and edge cases
- Structured bug reports with reproduction steps, expected vs. actual behavior, severity and status
- Rate limiting and public-demo abuse protection
- Swagger/OpenAPI documentation and Postman testing
- GitHub Actions CI/CD
- Scheduled database-backed health checks
- Nightly sample-data reseeding for a predictable public demo
